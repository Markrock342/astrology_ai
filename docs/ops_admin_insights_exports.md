# Admin dates, aggregate insights and member CSV

Admin expiry inputs show Gregorian dd/mm/yyyy (for example 04/11/2026 = 4 November). The calendar stores ISO days internally and expiry remains end-of-day in Bangkok. Invalid dates and Buddhist years are rejected instead of silently setting a date centuries ahead. Existing member dates are not rewritten by deployment.

The reported 4 November/11 November case had the correct included-wallet and Free-subscription date in the database. The purchased pool had zero questions but retained its older 11 November timestamp. Profile/list/export views now ignore that stale purchased deadline when purchased balance is zero; the profile shows the included date separately. With two nonempty pools, the list/export shows the earliest finite deadline. The member expiry editor still changes all relevant active entitlements without granting questions.

Admin → Users exports a UTF-8 BOM CSV readable by Excel, with Email, latest purchased pack, purchase date, question expiry, remaining questions, status and signup date. Ranges use signup dates in Bangkok: 7/28/90/180/365 calendar days including today, current calendar month, or all. Staff accounts are excluded. Search/email and status filters apply; the current-package dropdown does not filter exports. Latest pack is the latest approved payment, even if it has since expired. Remaining questions exclude already-ended pools without changing wallets. Exports require admin + 2FA, have private/no-store headers, are audited, rate limited and protect against spreadsheet formula injection. More than 100,000 matching members requires a narrower range rather than silently truncating the file.

Admin → Feedback now returns satisfaction counts and aggregate insights only. It no longer returns member names/emails, message IDs, feedback reasons, or raw questions/answers through that endpoint. Processing scans non-deleted successful chat messages up to its start time, including all members rather than only thumbs-up/down messages. It redacts known member names/nicknames, emails and birth locations, plus common URL/email/number formats before model calls. For bounded processing, each message contributes up to 800 sanitized characters for questions or 2,000 for answers; every qualifying message is counted. Source IDs are local batch indexes; member IDs remain server-side for distinct-member counting. These masks reduce identifying information; they are not a formal guarantee that arbitrary free text cannot contain an identifier.

AI groups specific equivalent question intents and recurring answer statements, not broad categories like work/money/love. It reuses specific labels across batches and performs bounded synonym-merging passes without repeatedly compressing everything into general topics. Greetings and system messages are counted as processed text but excluded from the top questions/answers. If a model grouping is invalid or truncated, the job discards it and retries smaller complete batches (bounded depth), then merges identical labels without inflating counts. The server verifies complete, unique, in-range source IDs, computes counts from actual rows (never model-supplied counts), and suppresses groups from fewer than three distinct members. Up to 50 question groups and 50 answer groups are returned; insufficient data is shown as fewer groups, never fabricated topics. Deleted and failed answers are excluded. Unkeyed legacy standalone readings are included too. Keyed orphan readings are excluded: without their original chat, they cannot be distinguished from hard-deleted conversations. Linked/deleted chat readings are excluded from the extra source as well, preventing duplicates and resurfacing removed content.

An admin starts processing explicitly with ประมวลผลข้อมูลล่าสุด. A PostgreSQL advisory lock prevents duplicate concurrent jobs. Next.js `after` runs the work after the response on the persistent Coolify server. Private AppSetting `admin.chatInsights.v1` stores only progress and the aggregate result, not raw text/member membership. Progress is polled every five seconds, survives leaving the page, and a stale lease can be retried after 30 minutes. Failed jobs show a generic error and retain the previous aggregate. Admin AI usage is logged against the acting admin and does not debit member wallets. Generations use the site's configured enabled AI model and incur provider usage.

Validation: unit coverage for date ambiguity/leap years, stale empty pools, Bangkok range boundaries, CSV escaping, identity masking, unique/complete AI grouping and minimum-member suppression. Protected-route tests reject anonymous/non-admin reads and generation. Isolated PostgreSQL tests export 505 members across a UI-page boundary without wallet changes, verify job locking, read all valid messages, check provider prompts are masked and ensure the response contains aggregates only. The real production-bundle E2E also verifies saved/reloaded dates, CSV download, anonymous export denial and aggregate-only feedback rendering/API. CI runs all these before merge/deploy.
